PGBloom Locks

TTL distributed locks and leader election.

What it is

Locks are PostgreSQL rows with an owner, TTL, and ownership checks. Leader election is implemented as a lock on leader:<resource> with renewal.

Why it exists and when to use it

Use locks to coordinate concurrent workers sharing PostgreSQL. Do not hold a lock longer than its TTL without extending it, and do not use it as a substitute for database transactions.

Architecture and internal implementation

tryLock returns a boolean on the client; standalone tryLock returns acquisition details including holderId. Blocking lock retries with exponential backoff until its timeout. Related: /aiagent/queue, /aiagent/scheduler, /aiagent/configuration.

Public API and signatures

Client methods include tryLock, lock, unlock, acquireLeadership, releaseLeadership, and isLeader. Standalone exports additionally include createLockState, renewLeadership, getLockInfo, and extendLock.

Parameters and returns

Use the signatures above as the public contract. Optional values use the defaults in Configuration; successful asynchronous operations return the stated promise value, while mutations may return void, a count, an identifier, or a result object.

Errors, concurrency, and failure scenarios

Invalid inputs throw the package validation/configuration error for the relevant subsystem. PostgreSQL failures propagate as database errors. Concurrent behavior is controlled by PostgreSQL transactions, row locks, listener state, TTLs, or atomic updates as described above. Treat expiry, process termination, database outages, duplicate work, and cleanup races as expected failure scenarios.

When not to use it

Do not use this feature outside its runtime boundary, as a security decision, or as a replacement for a stronger external system when its documented durability and delivery model is insufficient.

Example

const acquired = await client.tryLock("resource:42");
if (acquired) {
  try { /* critical section */ } finally { await client.unlock("resource:42", holderId); }
}
